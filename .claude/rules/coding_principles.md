# 코딩 행동 4원칙

LLM이 흔히 범하는 실수를 줄이기 위한 행동 지침. **모든 코드 변경에 적용**되며, 특히 coder가 Edit/Write로 파일을 변경할 때 작업 지시 말미에 인용된다.

> **Tradeoff**: 이 원칙들은 속도보다 신중함 쪽으로 편향돼 있다. 자명한 1줄 수정에는 판단해서 생략 가능.

## 1. 생각하고 코딩하기 (Think Before Coding)

**가정하지 마. 헷갈림을 숨기지 마. 트레이드오프를 드러내.**

구현 전:
- 가정을 명시적으로 말한다. 불확실하면 묻는다.
- 해석이 갈리면 옵션을 제시한다 — 조용히 하나를 고르지 않는다.
- 더 단순한 길이 보이면 말한다. 정당하면 푸시백한다.
- 모호하면 멈춘다. 무엇이 헷갈리는지 이름 붙이고 묻는다.

## 2. 단순함 우선 (Simplicity First)

**문제를 해결하는 최소 코드. 사변적인 것 없음.**

- 요청되지 않은 기능 추가 금지.
- 단발 사용 코드의 추상화 금지.
- 요청되지 않은 "유연성"·"설정 가능성" 금지.
- 일어날 수 없는 시나리오를 위한 에러 핸들링 금지.
- 200줄 썼는데 50줄로 가능하다면 다시 쓴다.

자문: "시니어 엔지니어가 이걸 보면 과복잡하다고 할까?" → 그렇다면 단순화한다.

## 3. 외과적 변경 (Surgical Changes)

**필요한 것만 손댄다. 자기가 만든 흔적만 치운다.**

기존 코드를 편집할 때:
- 인접한 코드·주석·포맷을 "개선"하지 않는다.
- 깨지지 않은 것을 리팩토링하지 않는다.
- 기존 스타일을 따른다 — 본인이라면 다르게 했더라도.
- 무관한 dead code를 발견하면 **언급만 한다 — 삭제하지 않는다**.

변경이 orphan을 만들었을 때:
- **본인의 변경**으로 미사용이 된 import/변수/함수만 제거한다.
- 사전에 존재하던 dead code는 지시 없이 제거하지 않는다.

검증 질문: 변경된 모든 줄이 사용자 요청에 **직접** 트레이스되는가?

## 4. 목표 주도 실행 (Goal-Driven Execution)

**성공 기준을 정의한다. 검증될 때까지 루프.**

작업을 검증 가능한 목표로 변환:
- "validation 추가" → "잘못된 입력에 대한 테스트를 쓰고, 통과시킨다"
- "버그 고쳐" → "재현 테스트를 먼저 쓰고, 통과시킨다"
- "X 리팩토링" → "전후로 테스트가 통과하는지 확인한다"

다단계 작업이면 간단한 계획을 명시:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준은 독립 루프를 가능하게 한다. 약한 기준("동작하게 해줘")은 끊임없는 명확화 요청을 부른다.

---

**이 원칙들이 작동하고 있다면**: diff에 불필요한 변경이 줄고, 과복잡으로 인한 재작성이 줄고, 명확화 질문이 실수 **이후가 아니라 이전에** 나온다.

## 본 베이스에서 적용 지점

- **coder** → 변경 보고 말미에 본 원칙(특히 §2·§3)을 어떻게 지켰는지 한 줄씩 자기 점검 ([coder.md](../agents/coder.md) "행동 4원칙 자기 점검" 출력 절 참조).
- **planner** → 단계 분해·옵션 비교 시 본 원칙으로 자가 점검 (특히 §1·§2).
- **critic** → 검증 시 본 원칙 위반을 결함(Defect) 사유로 명시 (특히 §2 과복잡·§3 범위 외 변경).
- **메인 에이전트** → 단순 작업을 full 4단계로 전환하기 전 §3에 비춰 "정말 4단계가 필요한가" 한 번 더 점검.
