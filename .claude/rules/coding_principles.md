# 코딩 행동 3원칙

LLM이 흔히 범하는 실수를 줄이기 위한 행동 지침. **모든 코드 변경에 적용**된다.

> **Tradeoff**: 이 원칙들은 속도보다 신중함 쪽으로 편향돼 있다. 자명한 1줄 수정에는 판단해서 생략 가능.

## 1. 생각하고 코딩하기 (Think Before Coding)

**가정하지 마. 헷갈림을 숨기지 마. 트레이드오프를 드러내.**

구현 전:
- 가정을 명시적으로 말한다. 불확실하면 묻는다.
- 해석이 갈리면 옵션을 제시한다 — 조용히 하나를 고르지 않는다.
- 더 단순한 길이 보이면 말한다. 정당하면 푸시백한다.
- 모호하면 멈춘다. 무엇이 헷갈리는지 이름 붙이고 묻는다.

## 2. 단순함 우선 (Simplicity First)

**문제를 해결하는 최소 코드. 사변적인 것 없음.**

- 요청되지 않은 기능 추가 금지.
- 단발 사용 코드의 추상화 금지.
- 요청되지 않은 "유연성"·"설정 가능성" 금지.
- 일어날 수 없는 시나리오를 위한 에러 핸들링 금지.
- 200줄 썼는데 50줄로 가능하다면 다시 쓴다.

자문: "시니어 엔지니어가 이걸 보면 과복잡하다고 할까?" → 그렇다면 단순화한다.

## 3. 목표 주도 실행 (Goal-Driven Execution)

**성공 기준을 정의한다. 검증될 때까지 루프.**

작업을 검증 가능한 목표로 변환:
- "validation 추가" → "잘못된 입력에 대한 테스트를 쓰고, 통과시킨다"
- "버그 고쳐" → "재현 테스트를 먼저 쓰고, 통과시킨다"
- "X 리팩토링" → "전후로 테스트가 통과하는지 확인한다"

다단계 작업이면 간단한 계획을 명시:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준은 독립 루프를 가능하게 한다. 약한 기준("동작하게 해줘")은 끊임없는 명확화 요청을 부른다.

---

**이 원칙들이 작동하고 있다면**: 과복잡으로 인한 재작성이 줄고, 명확화 질문이 실수 **이후가 아니라 이전에** 나온다.

## 본 베이스에서 적용 지점

이 베이스는 서브에이전트가 없다 — 메인이 조사·수정·검증을 다 하므로 세 원칙이 **한 에이전트 안에서** 순서대로 작동한다.

- **조사·설계할 때** → 가정을 명시하고, 해석이 갈리면 옵션으로 편다(§1). 무엇을 어디까지 고칠지 미리 좁히지 말고 살핀 뒤, 범위는 사용자 확인으로 정한다.
- **수정할 때** → §2(단순함)가 핵심. 합의된 범위 안에서만 치고, 요청되지 않은 기능·추상화를 더하지 않는다.
- **검증할 때** → §3(목표 주도). 성공 기준을 정하고 그 기준으로 자기 변경을 점검한다. 과복잡을 스스로 결함으로 잡는다.

> 서브에이전트가 없으므로 역할 분리 안전망이 없다. 대신 메인이 수정 후 스스로 §3 기준으로 점검하고, 자신 없으면 사용자에게 확인 체크리스트를 넘긴다.
